4.4 NULL: the value that is not a value

ch04-s4-0

Five customers have no email address. In the table, their email is NULL (FR: NULL (valeur absente)). NULL means unknown or missing. It is not zero, it is not an empty text '', it is "we do not know".

analogy

Imagine a form where somebody did not answer the question "What is your age?". You cannot say the age is 0. You cannot say it is equal to the age of another person who also did not answer: you simply do not know either age. SQL reasons exactly like this.

ch04-s4-1

4.4.1 Three-valued logic

Because of NULL, a condition in SQL can be true, false or unknown (shown as NULL). Any comparison with NULL is unknown, and where keeps only rows where the condition is true.

select null = null as a, null <> 1 as b, null is null as c, 1 + null as d;

Even null = null is not true: two unknown values are not known to be equal. Arithmetic with NULL gives NULL. The only correct test is is null / is not null.

trap

where email = null runs without any error, and returns zero rows. The comparison is unknown for every row, so no row is kept. A query that is wrong but does not fail is the most dangerous kind of bug. Always write is null or is not null.

ch04-s4-3

4.4.3 The NOT IN trap

x not in (1, 2, null) means x <> 1 and x <> 2 and x <> null. The last part is unknown for every row, so the whole condition is never true:

select count(*) from jaffle_shop.customers where id not in (1, 2);        -- 98
select count(*) from jaffle_shop.customers where id not in (1, 2, null);  -- 0 !
ch04-c31 sql

In real life the NULL does not come from a list you typed, but from a subquery such as where id not in (select user_id from ...). If one user_id is NULL, the query silently returns nothing. The anti-join pattern of Section 4.8 (or not exists, seen in Section 4.10) does not have this problem.

ch04-s4-4

4.4.4 Replacing NULL: coalesce and nullif

coalesce(a, b, c, ...) returns the first value that is not NULL. It is the standard way to give a default value:

select id, first_name, coalesce(email, 'no email') as email
from jaffle_shop.customers
where id in (15, 17, 34);

nullif(a, b) does the reverse: it returns NULL when a = b, otherwise a. The classic use is to avoid division by zero: revenue / nullif(n_orders, 0) returns NULL instead of failing when there are no orders. (Most warehouses raise an error on division by zero. DuckDB returns inf with /, which is not better for a report.)

ch04-s4-5

4.4.5 count(*) versus count(column)

This difference is small, important, and loved by exam writers.

  • count(*) counts rows, whatever they contain.

  • count(email) counts rows where email is not NULL.

select
    count(*) as all_rows,
    count(email) as with_email,
    count(*) - count(email) as missing
from jaffle_shop.customers;

The same rule holds for all aggregate functions: sum, avg, min, max ignore NULLs. avg of (10, NULL, 20) is 15, not 10.

dbt

dbt's built-in not_null data test (Chapter 18) is just a query like select * from my_model where my_column is null. If it returns rows, the test fails, and dbt reports how many rows failed. Understanding NULL is understanding half of dbt testing. When you build the customers model later, you will also use coalesce to turn "no orders" into 0 instead of NULL.
