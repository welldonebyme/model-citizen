7.2 Sources: declaring the raw data

ch07-s2-1

7.2.1 Why declare sources?

dbt does not load data. Other tools (Fivetran, Airbyte, a Python script, or our setup.sql) copy the data of applications into the warehouse, in raw schemas: jaffle_shop and stripe in our database. dbt starts from there.

You could write from jaffle_shop.orders in a model, and it would work. But dbt would not know that the model depends on raw data. Instead you declare each raw table once, in a YAML file, and read it with the Jinja function source(). The benefits:

  • the raw table becomes a node of the DAG: you can see which models use it, and select them (source:stripe+);

  • its location is written in one place: if the loader moves the table to another schema, you change one line of YAML;

  • you can describe it, test it (Chapter 18) and check its freshness (Chapter 21).

ch07-s2-2

7.2.2 Our two source files

dbt finds sources in any YAML file under models/, under the key sources:. We follow the common convention: one file per source, in the staging folder of that source, called _<source>__sources.yml (the leading underscore keeps the YAML files at the top of the folder listing).

models/staging/jaffle_shop/_jaffle_shop__sources.yml
version: 2

sources:
  - name: jaffle_shop
    description: Raw data copied every night from the Jaffle Shop web application.
    schema: jaffle_shop   # same as the source name, so this line is optional
    tables:
      - name: customers
        description: One row per customer account.
      - name: orders
        description: One row per order. user_id points to customers.id.
      - name: order_items
        description: One row per product line inside an order.
      - name: products
        description: The product catalogue. Prices are in cents.
ch07-c1 yaml
models/staging/stripe/_stripe__sources.yml
version: 2

sources:
  - name: stripe
    description: Raw data from Stripe, our payment provider.
    tables:
      - name: payments
        description: One row per payment attempt. Amounts are in cents.
ch07-c2 yaml

A source (jaffle_shop) is a group of raw tables, usually everything that one loader brings from one system. Each item under tables: is a source table. The first line version: 2 is a leftover of old dbt versions; it is optional in dbt 1.11, but you will see it in most projects.

ch07-s2-3

7.2.3 source() and what it compiles to

In a model you write {{ source('jaffle_shop', 'orders') }}: two arguments, the source name and the table name, both as declared in YAML. dbt replaces the call with the full name of the table:

[figure ch07-fig2 -> figures/ch07-fig2.svg] alt: dbt compiles {{ source('jaffle_shop', 'orders') }} into the full table name "practice"."jaffle_shop"."orders": database (the target database), schema (default: the source name) and identifier (default: the table name).

  • database: without a database: key, the database of the current target (practice for us).

  • schema: without a schema: key, the source name. Our stripe source has no schema: line, so dbt uses the schema stripe.

  • identifier: without an identifier: key, the table name.

You can check it any time with dbt compile (Section 7.7). The compiled staging model shows select * from "practice"."jaffle_shop"."orders".

trap

Two arguments, always. source('orders') is wrong; you need source('jaffle_shop', 'orders') (trap T38). ref() is different: it usually takes one argument, the model name (trap T37: the two functions are not interchangeable). The schema defaults to the source name, not to your target schema (trap T39). Without schema:, the source stripe is read from the schema stripe, never from dbt_adnane.

ch07-s2-4

7.2.4 When the names differ: schema and identifier

In real warehouses the raw names are often ugly (raw_shopify_v2, ORDERS_EXPORT_2024). You choose a clean name for source() and map it to the real location. We tested it with a temporary file:

models/staging/_demo_sources.yml (temporary, not committed)
version: 2

sources:
  - name: shop_raw            # the name you type in source()
    schema: jaffle_shop       # the real schema in the database
    tables:
      - name: raw_orders      # the name you type in source()
        identifier: orders    # the real table name

7.2.5 All source properties

KeyLevelMeaning
namesource, tableRequired. The names you use in source('<source>', '<table>').
descriptionsource, table, columnFree text (Markdown) shown in the documentation.
databasesourceDatabase (or project, catalog) of the raw tables. Default: the target database.
schemasourceSchema (or dataset) of the raw tables. Default: the source name.
identifiertableReal table name in the warehouse. Default: the table name.
loadersourceFree text saying which tool loads the data (fivetran, airbyte…). Documentation only.
quotingsource, tabledatabase, schema, identifier: true or false, whether dbt puts the names in double quotes.
tablessourceThe list of source tables.
columnstableColumn names with descriptions and data tests.
data_teststable, columnTests on the raw data (Chapter 18).
configsource, tableenabled, tags, meta, freshness, loaded_at_field, event_time… (Chapters 10, 16, 21).

A last test shows database, loader and quoting together. With database: archive, loader: nightly_copy_script and quoting: {identifier: false} on the shop_raw source, the same source('shop_raw', 'raw_orders') compiled to:

Result
Compiled inline node is:
select count(*) as n from "archive"."jaffle_shop".orders
ch07-c6 output small

The database changed, the identifier lost its quotes, and loader changed nothing in the SQL (it only appears in the documentation). Quoting matters on Snowflake, where quoted names become case sensitive: the default is false on Snowflake and true on most other adapters, DuckDB included. You rarely need to change it.

deep

Since dbt 1.10, freshness, loaded_at_field, meta and tags of a source belong under config:. The old place (directly under the source or table) still works but is deprecated. On Snowflake, BigQuery, Databricks and Redshift, dbt 1.11 prints a deprecation warning for the old place; with DuckDB, dbt skips this check, so you would see nothing. Write the new form from the start.
