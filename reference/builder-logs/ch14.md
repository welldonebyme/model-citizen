## 1. fct_orders becomes incremental

Strategy chosen: `merge` with `unique_key='order_id'`. Why: an order can CHANGE after it was first loaded
(placed -> shipped, a payment arrives later), so a new version of a row must REPLACE the old one (upsert).
`append` would create duplicates; `delete+insert` would also be correct (it is dbt-duckdb's default when a
unique_key is set); `merge` is the usual choice on Snowflake/BigQuery/Databricks and is available on DuckDB >= 1.4.
The filter uses `loaded_at`: every changed row in the source gets a new _loaded_at (see day2.sql).

## 2. Microbatch: models/marts/fct_order_items_daily.sql + event_time configs

event_time is configured on the upstream nodes (sources orders/payments, stg_jaffle_shop__orders, stg_stripe__payments,
int_orders__enriched, fct_orders, fct_order_items) - needed so that a microbatch model reading them gets filtered per
batch, and for `--sample` (Chapter 16). New file `models/intermediate/_intermediate__models.yml`.

### models/marts/fct_order_items_daily.sql

```bash
$ cat models/marts/fct_order_items_daily.sql
```
```text
{#
    Microbatch: dbt splits the work into batches of one month (batch_size) on
    order_date (event_time), from 2025-01-01 (begin). Each batch only reads the
    rows of fct_order_items whose event_time is inside the batch.
    A normal run re-processes the current batch and 1 previous batch (lookback).
#}
{{
    config(
        materialized='incremental',
        incremental_strategy='microbatch',
        event_time='order_date',
        begin='2025-01-01',
        batch_size='month',
        lookback=1
    )
}}

with

order_items as (

    select * from {{ ref('fct_order_items') }}

)

select
    order_date,
    product_id,
    product_name,
    category,
    count(distinct order_id) as number_of_orders,
    sum(quantity) as quantity,
    sum(line_amount) as revenue

from order_items
group by 1, 2, 3, 4
```
