## 4. The production build was only a PARTIAL SUCCESS: diagnose the microbatch failure
This was the FIRST full build of fct_order_items_daily since persist_docs was added (Chapter 20): 22 batches, run in parallel
(concurrent batches, 4 threads). 12 batches failed with 'Catalog write-write conflict on alter'. The log shows which statement:

### logs/dbt.log just before the first conflict: the COMMENT ON TABLE written by persist_docs

```bash
$ L=$(grep -n 'write-write' logs/dbt.log | head -1 | cut -d: -f1); sed -n "$((L-6)),$((L))p" logs/dbt.log
```
```text
  
  comment on table "practice"."marts"."fct_order_items_daily" is $dbt_comment_literal_block$Quantity and revenue per day and product (microbatch incremental model).$dbt_comment_literal_block$;

  
21:35:02.334059 [debug] [Thread-4 (]: On model.jaffle_dbt.fct_order_items_daily: COMMIT
21:35:02.334360 [debug] [Thread-1 (]: SQL status: OK in 0.000 seconds
21:35:02.334860 [debug] [Thread-3 (]: DuckDB adapter: duckdb error: TransactionContext Error: Catalog write-write conflict on alter with "fct_order_items_daily"
```

Cause: every batch runs `comment on table ...` (persist_docs) and the post-hook on the SAME table at the same time; DuckDB allows
only one writer to change a table's catalog entry at a time. In dev the daily runs only had 2 batches, so it was not visible.
Fix: run the batches one after the other with `concurrent_batches=False` (microbatch config, dbt 1.9+).

Finding: dbt clone FAILED for the marts: 'Binder Error: Can only vacuum or analyze base tables'. On DuckDB, clone creates a
VIEW (no zero-copy clone), and the marts' post-hook `analyze {{ this }}` (Chapter 10) also runs during dbt clone; ANALYZE refuses a

clone, with `flags.WHICH` (the name of the running command).
